### Блок 5.2. Resource math: прикидываем байты, RPS и деньги “на салфетке”

В реальной жизни от архитектора ждут не только “правильной схемы сервисов”, но и умения быстро прикинуть:
сколько это займёт места, какой будет RPS, выдержит ли диск/сеть и во сколько это всё выльется в инфраструктуре.

Здесь не про суперточные расчёты, а про порядок величин: понять, о каких десятках гигабайт и тысячах RPS идёт речь, ещё до того, как вы что-то задеплоили.

#### 5.2.1. Размер данных: разбираем на примере ledger

Возьмём таблицу транзакций в финсервисе:

```text
ledger_entries (
  id BIGSERIAL PK            → 8 байт
  tx_id UUID                 → 16 байт
  account_id BIGINT          → 8 байт
  amount_cents BIGINT        → 8 байт
  balance_snapshot BIGINT    → 8 байт
  type SMALLINT              → 2 байта
  created_at TIMESTAMP(6)    → 8 байт
  metadata JSONB (сред.)     → ~200 байт
)
```

Сумма “голых” данных:

- 8 + 16 + 8 + 8 + 8 + 2 + 8 + 200 = 258 байт.

Добавляем накладные расходы PostgreSQL:

- заголовок строки ~23 байта;
- выравнивание до кратного 8.

Округлим до ~288 байт на строку.

Теперь считаем порядок:

- пусть у нас 10 млн переводов;
- на каждый перевод пишем 2 записи в ledger → 20 млн строк.

Тогда:

- данные: 20 000 000 × 288 байт ≈ 5.8 ГБ;
- индексы:

    - PK по id: примерно 0.3 × размера данных;
    - индексы по tx_id / account_id: ещё ~0.5 ×.

Итого по таблице + индексам получаем порядка:

- таблица ≈ 5.8 ГБ;
- индексы ≈ 2–3 ГБ;
- плюс WAL / резерв на рост.

То есть на 10 млн переводов разумно закладывать ~10–12 ГБ только под ledger.
Если планируется рост до 100 млн транзакций — речь уже про сотни гигабайт, шардирование и/или отдельный кластер под ledger.

Именно такой порядок оценок от тебя хотят на собесе, когда спрашивают “а сколько это примерно будет весить?”

#### 5.2.2. RPS и сеть: сколько трафика генерирует приложение

Теперь прикинем нагрузку.

Пусть типичный запрос на API выглядит так (упрощённо):

```json
{
  "from_account": 12345,
  "to_account": 54321,
  "amount": 100,
  "idempotency_key": "uuid"
}
```

С учётом JSON-обвязки, ключей, кавычек получаем ~100–150 байт тела.
К этому добавляем:

- HTTP-заголовки: ~500–800 байт;
- кусок TLS-оверхода и прочую обвязку.

В сумме:

- 1 входящий запрос ≈ 0.8–1.0 КБ;
- ответ будет сравнимого порядка.

Грубая формула для RPS:

```text
RPS ≈ DAU - avg_requests_per_user_per_day / 86 400
```

Пример 1: 100k DAU, 20 запросов в день на пользователя:

- RPS ≈ 100 000 - 20 / 86 400 ≈ 23 RPS.

Пример 2: 1M DAU, те же 20 запросов:

- RPS ≈ 1 000 000 - 20 / 86 400 ≈ 231 RPS.

Трафик по сети:

```text
Traffic_in ≈ RPS - avg_request_size
Traffic_out ≈ RPS - avg_response_size
```

Если взять 1 КБ на запрос и 2 КБ на ответ:

- для 231 RPS это всего ~231 КБ/с вход и ~462 КБ/с выход, то есть единицы Мбит/с — ерунда для любого нормального датацентра.

Вывод:

- по сети мы почти никогда не упираемся на уровне “обычного веб-сервиса”;
- настоящая боль обычно в диске (IOPS + fsync) и в CPU/LOCK’ах БД.

#### 5.2.3. Прикидка по CPU и деньгам

CPU считать на глаз сложнее, но логика простая:

- берём цель по p95 latency и RPS;
- измеряем, сколько CPU/ядр нужно одному инстансу, чтобы выдерживать, скажем, 100 RPS с нужным p95;
- масштабируем по формуле из Little’а (нужен запас → не грузим выше 60–70% CPU).

Пример грубого прикида для платёжного сервиса:

- расчёты выше дали нам, что 1 БД-инстанс держит 20 млн ledger-записей и RPS в пару сотен;
- по нагрузочным тестам видим, что Postgres на 8 vCPU / 32 GB при RPS ≈ 300 держит p95 < 50 ms, при загрузке CPU ≈ 60%;
- хотим запас на рост до 600 RPS → нужно либо:

    - удвоить количество приложенческих нод (если упираемся в app-слой),
    - либо вынести часть нагрузки в кэш и/или шардировать/реплицировать БД.

Дальше это переводится в деньги:

- БД-нода класса “8 vCPU / 32 GB RAM / быстрый SSD” — это десятки–сотни долларов в месяц в любом облаке;
- плюс несколько app-нод поменьше (по 2–4 vCPU, 8–16 GB);
- плюс Redis-кластер.

Не принципиально, будешь ли ты считать по AWS, GCP или bare-metal ценам — важен именно навык:

- прикинуть размер таблиц;
- прикинуть RPS и трафик;
- понять, куда упирается система (диск, CPU, сеть);
- и назвать порядок стоимости: “это инфраструктура на несколько сотен / пару тысяч долларов в месяц при таких-то SLA”.

На архитектурных собесах это и есть ожидаемый уровень: не точный прайс-лист, а внятный, численный sanity-check, что система вообще реалистична и влезает в здравые бюджеты.
