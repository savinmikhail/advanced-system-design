## Обзор пайплайна

Сначала верхнеуровнего расскажу как система работает

- Nginx формирует JSON‑логи и выводит их в stdout. 
- Promtail автоматически находит контейнеры через Docker‑socket, фильтрует поток nginx и разбирает JSON‑логи. 
  Он же отдаёт метрику latency в Prometheus, а сами логи пушит в Loki.
- Loki хранит логи и индексирует их 
- Prometheus опрашивает Promtail и собирает метрики
- Grafana отображает всё на дашборде

## Что важно в настройках каждого слоя

### Nginx

- В `docker/nginx/nginx.conf` определён формат `json_combined`: каждая строка лога — валидный JSON с набором полей (время, адрес, метод, URI, статус и т.д.) 
  и ключом `request_time`, где фиксируется, сколько секунд Nginx потратил на обработку запроса.
- Логи пишутся в `/dev/stdout` с помощью `access_log /dev/stdout json_combined;`, поэтому Docker может их прочитать.
- Другие директивы (`sendfile on`, `tcp_nodelay on`, `server_tokens off`) не влияют на метрики и оставляются без подробного разбора.

### Promtail

- В `docker/promtail/config.yml` задан discovery через Docker‑socket (`docker_sd_configs`), 
  поэтому агент автоматически отслеживает появление и исчезновение контейнеров.
- Блок `match` выбирает только stdout‑поток контейнера nginx по лейблам (`{service="nginx", stream="stdout"}`).
- Далее идут стадии:

   - `json` разбирает строку лога как JSON и достаёт поле `request_time`;
   - `metrics` строит гистограмму `nginx_request_time_seconds` (Promtail добавляет префикс `promtail_custom_`), 
     определяя бакеты `[0.005, 0.01, 0.025, …, 10]` — это интервалы, в которые будут попадать значения времени отклика. 
     Гистограмма нужна, чтобы Grafana могла построить p50/p99 через `histogram_quantile`.
- В секции `relabel_configs` переименовываются служебные лейблы Docker в удобные `container`, `service`, `compose_project` и `stream`.
  Эти лейблы передаются и в Loki, и в метрики.
- Параметр `clients` указывает на Loki (`http://loki:3100/loki/api/v1/push`),
  а блок `server` включает HTTP‑сервер на порту 9080 — здесь Prometheus забирает метрики.

### Loki

- В `docker/loki/config.yml` лежат настройки локи, но там нет ничего специфического для нашей задачи. это вполне дефолтный конфиг с настройками репликации/индексов

### Prometheus

- В `docker/prometheus/prometheus.yml` задаются источники метрик. 
  тут нас интересует job `promtail`: Prometheus обращается к `promtail:9080` и получает метрику `promtail_custom_nginx_request_time_seconds_bucket` с гистограммой задержек.
- Интервал опроса (`scrape_interval: 15s`) определяет частоту обновления метрик.

### Grafana

- В `docker/grafana/provisioning/datasources` настроены два источника: 
  - Loki (`uid: loki`, proxy‑доступ через `http://loki:3100`) 
  - Prometheus (`uid: prometheus`, по адресу `http://prometheus:9090`).
- Дашборд `HTTP RPS & Latency (Nginx/Loki)` содержит панели:

   - Requests per second: запрос `sum(rate({service="nginx"}[1m]))` в Loki, 
     который просто подсчитывает количество записей логов nginx за минуту — каждый лог соответствует одному HTTP‑запросу.
   - Latency (p50 / p99): два запроса `histogram_quantile(0.5, ...)` и `histogram_quantile(0.99, ...)` вычисляют 50‑й и 99‑й перцентили.
   - HTTP 5xx per minute: Loki‑запрос фильтрует логи с кодами 500–599 и подсчитывает их за минуту.
   - 5xx Error Rate (%): отношение количества 5xx‑ошибок к общему числу запросов
     (`100 - sum(rate({service="nginx"} | json | status >= 500 and status < 600 [5m])) / sum(rate({service="nginx"}[5m]))`).

## Итог

Эти метрики нужны не для «красивых графиков», а для оперативного обнаружения проблем. 

RPS (Requests per second) позволяет понять, какая фактическая нагрузка на сервис и соответствуют ли емкость и настройки ожиданиям.

Latency (p50/p99) показывает, сколько времени пользователи реально ждут ответа, 
и помогает заметить деградацию производительности до того, как она выльется в жалобы. 

Error rate (в частности, процент 5xx) — это индикатор серьёзных сбоев; 
если доля ошибок начинает расти, это означает, что часть клиентов получает неработающий сервис. 

Мониторинг этих показателей в реальном времени даёт возможность быстро реагировать — расширить инфраструктуру, 
откатить проблемный релиз или наладить кэширование — прежде чем пользователи начнут массово уходить или писать в поддержку.
