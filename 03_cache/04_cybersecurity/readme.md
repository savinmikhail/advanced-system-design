## Блок 4.5. Кибербезопасность в кеше (boosty)

Кэш — это не только ускорение. Это ещё и поверхность атаки: один неверный ответ может “размножиться” на тысячи пользователей.

### 1) Cache poisoning

**Cache poisoning** — когда в кэше оказывается неправильный ответ, и система начинает раздавать его всем.

Есть два разных источника проблемы.

#### 1.1 Application cache poisoning (чаще всего — наши баги)

Обычно это не атака, а ошибки проектирования кэша:

* неправильный cache key (не учли валюту/локаль/роль/AB-флаг);
* нет TTL или он слишком большой → stale/forever cache;
* гонки при обновлении (поздний запрос записал старое значение поверх нового);
* несовместимые форматы (v1/v2 пишут разные структуры).

Итог один: кэш перестаёт быть ускорителем и превращается в источник массовых “тихих” багов.

#### 1.2 Web cache poisoning (атака)

Это уже безопасность: злоумышленник добивается того, чтобы **CDN / reverse proxy закэшировал ответ**, который потом получат другие пользователи.

Обычно играют на:

* разнице в том, как backend и прокси интерпретируют запрос;
* заголовках и правилах кэширования (`Host`, `X-Forwarded-*`, `Vary`, компрессия и т.п.);
* ошибочной “публичности” ответа (когда приватный ответ кэшируется как общий).

### 2) Cache deception

**Cache deception** — злоумышленник **заставляет кэш считать приватную страницу статикой** и положить её в публичный кеш (часто через “расширение в URL” и странные пути).
Результат — утечка персональных данных: приватный контент становится доступен по “кэшируемому” URL.

### 3) Базовая защита

* для приватных страниц: `Cache-Control: no-store` или `private` (и проверять, что CDN это реально уважает);
* не кэшировать ответы, зависящие от `Cookie` / `Authorization`, если это явно не задумано (и корректно выставлять `Vary`);
* не кэшировать “по расширению URL”, кэшировать по явным правилам/роутам и типам контента;
* нормализация URL и защита от path traversal до кэширующего слоя;
* аудит cache key: что влияет на ответ — то обязано влиять на ключ.
