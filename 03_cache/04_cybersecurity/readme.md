## Блок 4.5. Кэш как поверхность атаки (кратко)

Кэш — это не только ускорение. Это ещё и “усилитель”: одна неправильная запись может размножиться на тысячи пользователей.
Поэтому при проектировании кэша важно думать не только про latency, но и про безопасность.

### 1) Cache poisoning (отравление кэша)

Это ситуация, когда в кэш попадает неправильный ответ, и потом его получают все.

Причины бывают двух типов:
- **наши баги**: неверный cache key (не учли роль/локаль/валюту/AB), слишком большой TTL, гонки при обновлении, несовместимые форматы v1/v2;
- **внешняя атака**: злоумышленник добивается, чтобы публичный кэш (CDN/прокси) сохранил “не тот” вариант ответа и раздавал его дальше.

### 2) Cache deception (обман кэша)

Здесь идея другая: злоумышленник заставляет кэш считать приватную страницу “публичной/кэшируемой” и положить её в общий кэш.
Результат — утечка: приватный контент становится доступен по кэшируемому URL.

### 3) Что с этим делать (без углубления)

Три базовых правила:
- **Приватное не кэшируем публично**: для приватных ответов должны быть явные запреты/ограничения кэширования.
- **Cache key должен учитывать всё, от чего зависит ответ**: роль/локаль/авторизация/AB — иначе риск подмены и утечек.
- **Кэшируем только то, что явно задумано кэшировать**: лучше “allowlist” по роутам/типам контента, чем “кэшируем почти всё”.

Этого понимания достаточно, чтобы не сделать кэш источником массовых багов и утечек.
