## Блок 4.5. Кибербезопасность в кеше (boosty)

### cache poisoning

**Cache poisoning** — это ситуация, когда в кэш попадает **неправильное, вредоносное или несогласованное значение**, и система начинает отдавать это “отравленное” состояние всем, кто к нему обращается.

Проблема коварная:
иногда это из-за наших багов, а иногда — прям полноценная атака.

Ниже разделяю чётко два мира.

#### 1. Application Cache Poisoning (наши собственные баги)

Это 90% случаев в обычных сервисах.

Причины:

##### Неправильный ключ

Ты закэшировал `/product?id=123`,
а забыл, что у запроса был query `?currency=usd`.
В итоге пользователи видят данные не своей валюты.

##### Отсутствие TTL

Ключ живёт месяцами. Данные давно поменялись, а кэш в параллельной вселенной.

##### Несогласованные форматы

Версия v1 пишет один JSON,
версия v2 — другой.
Половина сервисов не умеет читать новый формат → всё ломается.

##### Состояние гонки (race condition)

Поздний запрос перезаписывает новый кэш старым значением.

##### Write-behind / eventual-write глюки

Данные в Redis обновились, а запись в БД не прошла.

##### Неучтённые параметры запроса

Например:
разные роли, разные флаги, но ключ построен одинаково.

##### Прогрев кэша кладёт старые данные

Кривой скрипт прогрева промахнулся по источнику — получил старый snapshot и размазал по всему кэшу.

Эта форма poisoning не про безопасность.
Это про то, что **мы сами засрали кэш**, и теперь он гадит всем пользователям.

#### 2. Web Cache Poisoning (атака злоумышленника)

Это безопасность. Прям настоящая.

Сценарий такой:

1. Злоумышленник шлёт запрос с хитрыми заголовками или параметрами
2. CDN / Reverse Proxy / Varnish / Nginx кладёт **этот же ответ** в свой кэш
3. Все остальные пользователи получают **вредоносный контент**

Классические примеры:

##### XSS через кэш

Хакер подсовывает HTML/JS, CDN его кэширует, и дальше браузеры всех пользователей его исполняют.

##### Подмена страниц

Например, отдаём не тот HTML на главной.

##### Bypass авторизации

Если прокси кэшировал приватный ответ как публичный.

##### Манипуляция с заголовками

`X-Forwarded-Host`, `X-Original-URL`, `Accept-Encoding`, `Vary`, `Host` —
всё это используется в атаке, чтобы скормить прокси “уникальный” ответ, который попадёт в кэш.

##### Отравление параметров

Если ключ кэша строится на неподходящих параметрах, злоумышленник может добиться чужого контента.

Это то, что описывает PortSwigger, OWASP и все баг-баунти платформы.

### Cache Deception

Если **Web Cache Poisoning** — это когда хакер *кладёт неправильный контент в кэш*,
то **Cache Deception** — это когда хакер *заставляет прокси/ CDN закэшировать правильный контент под неправильным URL*.

Смысл:
злоумышленник получает **персональные данные чужого пользователя**,
потому что эти данные были ошибочно закэшированы как общедоступные.

Это не ошибка бизнес-логики — это ошибка в маршрутизации или в правилах кэширования.

#### Как это происходит (короткий сценарий атаки)

Представь:

1. У пользователя есть личная страница:

   ```
   /account
   ```

   Она **нельзя кэшировать** и всегда за авторизацией.

2. У CDN включён правила кэширования “всё, у чего есть расширение — отдаём как статику”
   например:

   ```
   /anything.js → cache
   /anything.css → cache
   /anything.jpg → cache
   ```

3. Хакер делает такой запрос:

   ```
   GET /account/../account.php.css
   ```

4. Приложение (backend) “нормализует” путь и всё равно отдаёт **контент страницы /account**.

5. А CDN видит расширение **.css** → и кладёт ответ в публичный кеш.

6. Теперь злоумышленник делает:

   ```
   GET /account/../account.php.css
   ```

   и получает контент личного кабинета жертвы.

Это и есть **Cache Deception**:
мы подсунули CDN “чужой личный контент” под видом *статического файла*.

#### Почему это так опасно?

* вы обходите авторизацию
* вы обходите приватность
* CDN кэширует “чужие” страницы
* злоумышленник может массово выкачивать профили

То есть это не просто “сломался UI” — это **утечка приватных данных**.

#### Типичные причины

##### Неправильная нормализация URL в backend

Backend думает, что `/user/123/../123` = `/user/123`.

##### Неверное правило кэширования в CDN

“Кэшируем всё с расширениями”.

##### Проброс параметров

Например:

```
/profile?format=json.css
```

Backend отдаёт JSON, CDN думает “это .css → в кэш”.

##### Неправильно настроенный Vary

Если нет `Vary: Cookie`, CDN считает ответ публичным.

---

#### Как защититься (коротко и по существу)

1. **Запрещать кэширование приватных страниц**

   ```
   Cache-Control: private, no-store
   ```

2. **Никогда не кэшировать запросы с Cookie/Auth headers**

3. **Не кэшировать по расширениям URL**
   а только по MIME-типу, который вернул backend.

4. **Нормализовать URL до попадания в CDN**
   чтобы CDN видел тот же путь, что и backend.

5. **Включать Vary: Authorization / Cookie**, где это нужно.

6. **Запретить path traversal** (`../`, `./`, `%2E%2E/`).
